# 2. 模块分层架构

## 分层概览

```

│                    表现层 (Presentation)                      │

│  └──────────────┘  └──────────────┘  └──────────────┘      │
└─────────────────────────────────────────────────────────────┘
```

**分层特点**:
- **严格单向依赖**: 上层依赖下层,下层不依赖上层
- **Namespace 隔离**: 每个模块使用独立命名空间
- **Instance Context**: 通过 `Instance.state()` 管理项目级状态
- **延迟初始化**: 使用 `lazy()` 工具实现按需加载

## 各层详解

- 处理用户交互和输入

## 依赖规则

### 允许的依赖

```
表现层 (CLI/Web/Routes)
    ↓
应用层 (SessionProcessor/ToolRegistry)
    ↓
领域层 (Session/Agent/Tool/Provider)
    ↓
基础设施层 (Storage/LSP/MCP/Bus/Log)
```

**具体规则**:
1. **表现层** 可以依赖 **应用层** 和 **领域层**
   - 示例: `RunCommand` → `SessionPrompt.prompt()`
   - 依据: `packages/opencode/src/cli/cmd/run.ts:265-272`

2. **应用层** 可以依赖 **领域层** 和 **基础设施层**
   - 示例: `SessionProcessor` → `Session.updatePart()` + `Bus.publish()`
   - 依据: `packages/opencode/src/session/processor.ts:84-98`

3. **领域层** 可以依赖 **基础设施层**
   - 示例: `Session.create()` → `Storage.write()`
   - 依据: `packages/opencode/src/session/index.ts:214`

4. **基础设施层** 不依赖其他层
   - 示例: `Storage` 只依赖 `fs` 和 `Bun.file`
   - 依据: `packages/opencode/src/storage/storage.ts:1-227`

---

### 禁止的依赖

❌ **领域层 → 表现层**
- 领域实体不应知道 UI 如何渲染
- 违反示例: `Session` 不应导入 `UI` 或 `Router`

❌ **基础设施层 → 领域层**
- 基础设施应保持通用性
- 违反示例: `Storage` 不应知道 `Session` 结构

❌ **领域层 → 应用层**
- 领域逻辑应独立于用例编排
- 违反示例: `Agent` 不应调用 `SessionProcessor`

❌ **跨模块直接访问状态**
- 所有状态访问通过公开接口
- 违反示例: 直接访问 `state()` 返回的内部状态

---

### 如何避免循环依赖

#### 1. Namespace 隔离
每个模块使用独立命名空间,避免相互引用:

```typescript
// 正确: 通过命名空间导出
export namespace Session {
  export function create() { ... }
}

// 使用
import { Session } from "./session"
Session.create()
```

**依据**: 所有核心模块都使用 Namespace 模式

#### 2. 事件驱动解耦
使用 `Bus` 事件总线避免直接依赖:

```typescript
// 发布事件
Bus.publish(Session.Event.Created, { info })

// 订阅事件
Bus.subscribe(Session.Event.Created, (payload) => {
  // 处理逻辑
})
```

**依据**: `packages/opencode/src/session/index.ts:215-217`

#### 3. 依赖注入
通过参数传递依赖,而非直接导入:


## 关键设计模式

### 1. Namespace Pattern
**用途**: 模块封装和命名空间隔离

```typescript
export namespace Session {
  export const Info = z.object({ ... })
  export type Info = z.infer<typeof Info>
  export async function create() { ... }
}
```

**优势**:
- 避免命名冲突
- 清晰的模块边界
- 支持嵌套命名空间

### 2. State Factory Pattern
**用途**: 项目级状态管理

```typescript
const state = Instance.state(
  async () => {
    // 初始化
    return { data: [] }
  },
  async (state) => {
    // 清理
    await cleanup(state)
  }
)
```

**优势**:
- 自动生命周期管理
- 项目隔离
- 延迟初始化

### 3. Event Sourcing Pattern
**用途**: 解耦模块通信

```typescript
const Event = {
  Created: BusEvent.define("session.created", Schema)
}

Bus.publish(Event.Created, { info })
```

**优势**:
- 松耦合
- 类型安全
- 易于扩展

### 4. Repository Pattern
**用途**: 数据访问抽象

```typescript
export namespace Session {
  export async function get(id: string) {
    return Storage.read<Info>(["session", projectID, id])
  }
  
  export async function list() {
    for (const item of await Storage.list(["session", projectID])) {
      yield Storage.read<Info>(item)
    }
  }
}
```

**优势**:
- 隐藏存储细节
- 统一访问接口
- 易于测试
