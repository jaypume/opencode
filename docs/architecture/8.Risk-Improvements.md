# 8. 风险点与改进建议

## 风险分类

- 🔴 **高风险**: 可能导致系统崩溃、数据丢失或安全漏洞
- 🟡 **中风险**: 可能导致功能异常、性能下降或用户体验问题
- 🟢 **低风险**: 影响有限,但需要关注和改进

---

## 架构风险

### 🔴 风险 1: Instance 状态内存泄漏

**风险描述**:
`Instance.state()` 创建的状态实例如果没有正确清理,会导致内存泄漏。当用户频繁切换项目或长时间运行时,内存占用会持续增长,最终可能导致系统崩溃。

**影响范围**:
- **影响模块**: Provider, LSP, MCP, Permission, 所有使用 `Instance.state()` 的模块
- **影响用户**: 所有 CLI 和 Desktop 用户,尤其是长时间运行或频繁切换项目的用户
- **影响数据**: 不会导致数据丢失,但会导致程序崩溃

**触发条件**:
- 用户频繁切换项目 (每次切换创建新 Instance)
- 长时间运行 (累积多个未清理的 Instance)
- Instance dispose 逻辑未正确执行

**当前缓解措施**:
- ✅ 已实施: `State.dispose()` 函数用于清理状态
- ✅ 已实施: `Instance.provide()` 使用 `defer()` 确保清理
- ❌ 未实施: 没有监控内存使用情况
- ❌ 未实施: 没有自动检测内存泄漏

**代码位置**:
- `packages/opencode/src/project/state.ts:3-66` - State 管理
- `packages/opencode/src/project/instance.ts:17-68` - Instance Context

**改进建议**:

1. **短期** (1-2 周) - P1:
   - 添加内存监控日志
   - 在 Instance dispose 时记录清理的状态数量
   - 添加单元测试验证 dispose 逻辑
   - **预期收益**: 可以及时发现内存泄漏,降低风险 30%
   - **实施成本**: 低 (1-2 天)

2. **中期** (1-2 月) - P2:
   - 实现 WeakMap 替代 Map 存储状态
   - 添加自动清理机制 (超过 1 小时未使用的 Instance)
   - 添加内存使用告警 (超过 500MB 发送警告)
   - **预期收益**: 自动防止内存泄漏,降低风险 70%
   - **实施成本**: 中等 (1 周)

3. **长期** (3-6 月) - P3:
   - 重构为 Singleton Pattern (每个项目只有一个 Instance)
   - 使用 Proxy 实现懒加载,减少内存占用
   - **预期收益**: 彻底消除内存泄漏风险
   - **实施成本**: 高 (需要重构大量代码)

### 🔴 风险 2: JSON 文件存储并发冲突

**风险描述**:
虽然实现了 Read-Write Lock,但在高并发场景下 (如多个 Session 同时更新),仍可能出现数据竞争。Lock 实现基于内存,无法跨进程保护,如果用户同时运行多个 OpenCode 实例,可能导致数据损坏。

**影响范围**:
- **影响模块**: Storage, Session, Message, Part
- **影响用户**: 同时运行多个 OpenCode 实例的用户
- **影响数据**: 可能导致数据损坏或丢失

**触发条件**:
- 用户同时运行多个 OpenCode CLI 实例
- 用户同时运行 CLI 和 Desktop 应用
- 多个 Session 同时写入同一文件

**当前缓解措施**:
- ✅ 已实施: Read-Write Lock (内存级别)
- ❌ 未实施: 跨进程文件锁
- ❌ 未实施: 数据完整性校验
- ❌ 未实施: 自动备份和恢复

**代码位置**:
- `packages/opencode/src/util/lock.ts:1-98` - Lock 实现
- `packages/opencode/src/storage/storage.ts:169-227` - Storage 实现

**改进建议**:

1. **短期** (1-2 周) - P1:
   - 添加文件锁 (使用 `fs.open()` with `O_EXCL` 标志)
   - 添加写入前的数据校验 (检查文件是否被修改)
   - 添加错误重试机制 (写入失败时重试 3 次)
   - **预期收益**: 降低数据损坏风险 50%
   - **实施成本**: 低 (2-3 天)

2. **中期** (1-2 月) - P2:
   - 实现 WAL (Write-Ahead Logging)
   - 添加自动备份 (每次写入前备份旧文件)
   - 添加数据完整性校验 (CRC32 或 MD5)
   - **预期收益**: 降低数据损坏风险 80%,支持数据恢复
   - **实施成本**: 中等 (1 周)

3. **长期** (3-6 月) - P3:
   - 迁移到 SQLite (支持 ACID 事务)
   - 实现跨进程锁 (使用文件锁或 IPC)
   - **预期收益**: 彻底消除并发冲突
   - **实施成本**: 高 (需要重写 Storage 层)

**改进建议**:

1. **短期** (1-2 周) - P2:

   - CLI 添加 Server 健康检查,崩溃时自动重启
   - **预期收益**: 降低服务中断风险 50%
   - **实施成本**: 低 (2-3 天)

### 🟡 风险 4: Event Bus 事件风暴

**风险描述**:
Event Bus 没有限流机制,在高频事件场景下 (如实时输出大量日志),可能导致事件积压,内存占用激增,甚至阻塞主线程。

**影响范围**:
- **影响模块**: Bus, Session, Storage, 所有订阅事件的模块
- **影响用户**: 执行大量输出的命令的用户 (如 `npm install`)
- **影响数据**: 不会导致数据丢失,但会导致性能下降

**触发条件**:
- 工具执行产生大量输出 (如 `npm install`, `git clone`)
- 多个 Session 同时活跃
- SSE 客户端处理速度慢

**当前缓解措施**:
- ✅ 已实施: 异步事件处理
- ❌ 未实施: 事件限流
- ❌ 未实施: 事件优先级
- ❌ 未实施: 背压机制

**代码位置**:
- `packages/opencode/src/bus/index.ts:1-100` - Event Bus
- `packages/opencode/src/server/server.ts:100-150` - SSE 推送

**改进建议**:

1. **短期** (1-2 周) - P2:
   - 实现事件合并 (相同类型的事件合并为一个)
   - 添加事件队列大小限制 (最多 1000 个)
   - 添加事件丢弃策略 (队列满时丢弃旧事件)
   - **预期收益**: 防止内存溢出,降低风险 60%
   - **实施成本**: 低 (2-3 天)

2. **中期** (1-2 月) - P3:
   - 实现事件优先级 (高优先级事件优先处理)
   - 实现背压机制 (客户端处理慢时暂停推送)
   - 添加事件采样 (高频事件只推送部分)
   - **预期收益**: 优化性能,降低风险 90%
   - **实施成本**: 中等 (1 周)
