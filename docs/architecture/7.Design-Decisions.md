# 7. 设计决策与权衡

## 决策概览

1. **Bun 作为主要运行时** - 高性能 JavaScript 运行时替代 Node.js
2. **SolidJS 作为前端框架** - 细粒度响应式替代 React/Vue
3. **Hono 作为 HTTP 框架** - 轻量级路由替代 Express/Fastify
4. **SSE 替代 WebSocket** - 单向流式通信
5. **JSON 文件存储替代数据库** - CLI/Desktop 本地持久化
6. **Monorepo + Turbo** - 多包管理策略
7. **Vercel AI SDK** - 统一 LLM 接口
8. **Tauri 替代 Electron** - 桌面应用框架
9. **MCP/LSP 协议集成** - 工具扩展性
10. **Git 作为快照系统** - 文件版本管理

---

## 决策 1: Bun 作为主要运行时

### 决策内容

选择了 **Bun** 而不是 **Node.js** 作为 CLI 和后端的主要运行时。

### 理由

1. **性能**: Bun 启动速度比 Node.js 快 4 倍,运行速度快 2~3 倍
   - CLI 启动时间: ~50ms (Bun) vs ~200ms (Node.js)
   - HTTP 服务器吞吐量: 提升 2~3 倍

2. **内置工具链**: 集成了包管理、测试、打包等工具
   - 无需 npm/yarn/pnpm
   - 无需 webpack/esbuild
   - 无需 jest/vitest

3. **原生 TypeScript 支持**: 无需编译,直接运行 `.ts` 文件
   - 开发体验更好
   - 减少构建步骤

4. **兼容性**: 完全兼容 Node.js API
   - 可以使用现有的 npm 包
   - 迁移成本低

5. **现代 API**: 内置 `Bun.file()`, `Bun.spawn()` 等高性能 API
   - 文件操作更快
   - 进程管理更简单

### 权衡

**优势**:
- ✅ 启动速度快 4 倍
- ✅ 运行性能提升 2~3 倍
- ✅ 内置工具链,减少依赖
- ✅ 原生 TypeScript 支持
- ✅ 开发体验更好

**劣势**:
- ❌ 生态系统较新 (2022 年发布)
- ❌ 部分 npm 包可能不兼容
- ❌ 社区资源相对较少
- ❌ 生产环境案例较少
- ❌ Windows 支持不如 Linux/macOS

### 替代方案

| 方案 | 优势 | 劣势 | 为何未选择 |
|-----|------|------|-----------|
| **Node.js** | 成熟稳定、生态丰富、广泛使用 | 启动慢、性能较差、需要额外工具 | 性能不满足需求,启动时间影响用户体验 |
| **Deno** | 安全性好、TypeScript 原生、标准库完善 | 生态系统小、npm 兼容性差 | npm 兼容性不足,迁移成本高 |
| **Node.js + esbuild** | 性能改善、成熟稳定 | 仍需额外工具、配置复杂 | Bun 提供更好的一体化解决方案 |

## 决策 2: SolidJS 作为前端框架

### 决策内容

选择了 **SolidJS** 而不是 **React** 或 **Vue** 作为 Web/Desktop UI 框架。

### 理由

1. **性能**: 细粒度响应式,无虚拟 DOM
   - 渲染速度比 React 快 2~3 倍
   - 内存占用减少 50%
   - 无 reconciliation 开销

2. **包体积**: 极小的运行时
   - SolidJS: ~7KB gzipped
   - React: ~40KB gzipped
   - Vue: ~35KB gzipped

3. **开发体验**: 类 React API,学习曲线低
   - 使用 JSX 语法
   - 熟悉的 Hooks 模式
   - 但更符合直觉 (无闭包陷阱)

4. **TypeScript 支持**: 一流的类型推断
   - 完整的类型定义
   - 泛型支持良好
   - 编译时类型检查

5. **SSR/SSG**: 内置 SolidStart,支持服务端渲染
   - 适合 Console 部分
   - SEO 友好

### 权衡

**优势**:
- ✅ 性能极佳 (2~3 倍于 React)
- ✅ 包体积小 (7KB vs 40KB)
- ✅ 细粒度响应式,精确更新
- ✅ 学习曲线低 (类 React API)
- ✅ TypeScript 支持好

**劣势**:
- ❌ 生态系统较小
- ❌ 社区资源少
- ❌ 第三方库较少
- ❌ 招聘难度较高
- ❌ 调试工具不如 React 完善

### 替代方案

| 方案 | 优势 | 劣势 | 为何未选择 |
|-----|------|------|-----------|
| **React** | 生态丰富、社区大、招聘容易 | 性能较差、包体积大、虚拟 DOM 开销 | 性能不满足需求,包体积影响加载速度 |
| **Vue 3** | 性能好、学习曲线低、文档完善 | 包体积较大、TypeScript 支持不如 SolidJS | 性能和包体积不如 SolidJS |
| **Svelte** | 编译时优化、无运行时、包体积小 | 生态系统小、响应式模型不同 | 细粒度响应式更适合实时更新场景 |
| **Preact** | 轻量 (3KB)、兼容 React | 性能不如 SolidJS、功能受限 | 性能和功能都不如 SolidJS |

   - Node.js
   - Cloudflare Workers
   - Deno

5. **现代 API**: 简洁的 API 设计
   - 链式调用
   - 中间件模式

### 权衡

**优势**:
- ✅ 性能极佳 (10 倍于 Express)
- ✅ 包体积小 (12KB vs 200KB)

## 决策 4: SSE 替代 WebSocket

### 决策内容

选择了 **Server-Sent Events (SSE)** 而不是 **WebSocket** 用于实时数据推送。

### 理由

1. **单向通信**: 只需要服务器 → 客户端推送
   - 客户端 → 服务器使用 HTTP POST
   - 无需双向通信

2. **简单性**: 基于 HTTP,无需额外协议
   - 使用标准 HTTP 连接
   - 无需 WebSocket 握手
   - 易于调试 (可以用 curl 测试)

3. **自动重连**: 浏览器原生支持
   - 断线自动重连
   - 无需手动实现

4. **HTTP/2 友好**: 可以复用 HTTP 连接
   - 减少连接数
   - 提高性能

5. **防火墙友好**: 基于 HTTP,穿透性好
   - 不会被企业防火墙阻止
   - 兼容性更好

### 权衡

**优势**:
- ✅ 实现简单 (基于 HTTP)
- ✅ 自动重连
- ✅ 易于调试
- ✅ 防火墙友好
- ✅ HTTP/2 复用连接

**劣势**:
- ❌ 单向通信 (但满足需求)
- ❌ 不支持二进制数据 (但不需要)
- ❌ 浏览器连接数限制 (HTTP/1.1 最多 6 个)

### 替代方案

| 方案 | 优势 | 劣势 | 为何未选择 |
|-----|------|------|-----------|
| **WebSocket** | 双向通信、低延迟、支持二进制 | 实现复杂、需要额外协议、调试困难 | 不需要双向通信,SSE 更简单 |
| **Long Polling** | 兼容性好、实现简单 | 性能差、服务器压力大 | 性能不满足需求 |
| **gRPC Streaming** | 性能好、类型安全、双向流 | 需要 Protobuf、浏览器支持差 | 浏览器支持不足 |

### 代码依据

- **服务器端**: `packages/opencode/src/server/server.ts:100-150`

## 决策 5: JSON 文件存储替代数据库

### 决策内容

选择了 **JSON 文件存储** 而不是 **SQLite/PostgreSQL** 用于 CLI/Desktop 的本地数据持久化。

### 理由

1. **零配置**: 无需安装数据库
   - 用户无需安装额外软件
   - 开箱即用

2. **可读性**: 文件可以直接查看和编辑
   - 方便调试
   - 方便备份和迁移
   - 用户可以手动修改

3. **跨平台**: 无需编译原生模块
   - 纯 JavaScript 实现
   - 无平台依赖

4. **简单性**: 无需 ORM 或查询语言
   - 直接读写 JSON
   - 代码简单

5. **性能**: 对于小数据集足够快
   - 会话数据通常 < 1000 条
   - 读写延迟 < 10ms

### 权衡

**优势**:
- ✅ 零配置,开箱即用
- ✅ 可读性好,易于调试
- ✅ 跨平台,无原生依赖
- ✅ 实现简单
- ✅ 性能足够 (小数据集)

**劣势**:
- ❌ 不支持复杂查询
- ❌ 不支持事务
- ❌ 大数据集性能差
- ❌ 并发控制困难
- ❌ 无索引支持

### 替代方案

| 方案 | 优势 | 劣势 | 为何未选择 |
|-----|------|------|-----------|
| **SQLite** | 支持 SQL、事务、索引 | 需要原生模块、跨平台问题 | 增加复杂度,对于小数据集不必要 |
| **LevelDB** | 性能好、嵌入式 | 需要原生模块、API 复杂 | 对于小数据集不必要 |
| **IndexedDB** (浏览器) | 浏览器原生、支持索引 | 只能在浏览器使用 | CLI/Desktop 无法使用 |
| **PouchDB** | 跨平台、同步支持 | 包体积大、性能一般 | 不需要同步功能 |

## 决策 6: Monorepo + Turbo

### 决策内容

选择了 **Monorepo** 架构,使用 **Bun Workspaces** 和 **Turbo** 进行构建管理。

### 理由

1. **代码共享**: 多个包共享代码
   - `@opencode-ai/sdk`: CLI, Desktop, Web 共用
   - `@opencode-ai/ui`: Desktop, Web 共用
   - `@opencode-ai/util`: 所有包共用

2. **统一依赖**: 版本管理更简单
   - 使用 Workspace Catalog
   - 避免版本冲突
   - 减少重复安装

3. **原子提交**: 跨包修改在一个 commit
   - 保证一致性
   - 简化 Code Review
   - 易于回滚

4. **构建优化**: Turbo 缓存和并行构建
   - 增量构建
   - 远程缓存
   - 并行执行

5. **开发体验**: 统一的工具链
   - 统一的 TypeScript 配置
   - 统一的 Lint 规则
   - 统一的测试框架

### 权衡

**优势**:
- ✅ 代码共享方便
- ✅ 依赖管理统一
- ✅ 原子提交,保证一致性
- ✅ 构建优化 (Turbo)
- ✅ 开发体验好

**劣势**:
- ❌ 仓库体积大
- ❌ CI/CD 时间长
- ❌ 初次 clone 慢
- ❌ IDE 性能影响
- ❌ 权限管理困难 (无法分包权限)

## 决策 9: MCP/LSP 协议集成

### 决策内容

选择了 **MCP (Model Context Protocol)** 和 **LSP (Language Server Protocol)** 作为工具扩展机制。

### 理由

1. **标准化**: 使用行业标准协议
   - MCP: Anthropic 提出的标准
   - LSP: Microsoft 提出的标准
   - 无需自定义协议

2. **可扩展性**: 支持第三方工具
   - MCP: 任何人都可以开发 MCP Server
   - LSP: 复用现有的 LSP Server
   - 无需修改 OpenCode 代码

3. **生态系统**: 复用现有工具
   - LSP: 支持所有主流语言 (TypeScript, Python, Go, Rust, ...)
   - MCP: 支持文件系统、数据库、API 等
   - 无需重复开发

4. **解耦**: 工具和核心分离
   - 工具在独立进程运行
   - 崩溃不影响主进程
   - 易于维护

5. **安全性**: 沙箱隔离
   - 工具无法直接访问文件系统
   - 需要通过权限系统
   - 减少安全风险

### 权衡

**优势**:
- ✅ 标准化协议,无需自定义
- ✅ 可扩展性强,支持第三方
- ✅ 复用现有生态系统
- ✅ 解耦,易于维护
- ✅ 沙箱隔离,安全性好

**劣势**:
- ❌ 协议复杂,学习曲线高
- ❌ 调试困难 (跨进程)
- ❌ 性能开销 (IPC)
- ❌ 错误处理复杂

### 替代方案

## 决策 10: Git 作为快照系统

### 决策内容

选择了 **Git** 而不是自定义快照系统用于文件版本管理。

### 理由

1. **成熟稳定**: Git 是行业标准
   - 经过 15+ 年验证
   - 极少 Bug
   - 性能优化完善

2. **高效存储**: 增量存储,节省空间
   - 只存储变更
   - 自动压缩
   - 去重

3. **内容寻址**: 基于 SHA-1 哈希
   - 保证数据完整性
   - 快速查找
   - 自动去重

4. **工具丰富**: 可以使用 Git 工具
   - `git diff` 查看变更
   - `git log` 查看历史
   - `git gc` 清理空间

5. **无需重复造轮子**: 复用成熟方案
   - 无需自己实现
   - 维护成本低

### 权衡

**优势**:
- ✅ 成熟稳定,经过验证
- ✅ 高效存储,增量压缩
- ✅ 内容寻址,保证完整性
- ✅ 工具丰富,易于调试
- ✅ 无需重复造轮子

**劣势**:
- ❌ 依赖 Git 二进制
- ❌ 学习曲线 (对于不熟悉 Git 的用户)

## 架构模式决策

### 决策 1: 采用分层架构

**理由**:
1. **清晰的职责分离**: UI, 业务逻辑, 数据访问分离
2. **易于测试**: 每层可以独立测试
3. **易于维护**: 修改一层不影响其他层
4. **易于扩展**: 可以替换某一层的实现

**权衡**:
- ✅ 代码组织清晰
- ✅ 易于扩展和维护
- ✅ 团队协作友好
- ❌ 增加了抽象层
- ❌ 初期开发稍慢
- ❌ 可能过度设计

**替代方案**:
- **六边形架构 (Ports & Adapters)**: 更灵活,但更复杂
- **CQRS**: 适合读写分离,但增加复杂度
- **微服务**: 适合大型系统,但对于 CLI 工具过于复杂

**依据**: `docs/architecture/2.Module-Layers.md`

---

### 决策 2: 采用事件驱动架构

**理由**:
1. **解耦**: 模块间通过事件通信,无直接依赖
2. **可扩展**: 新模块可以订阅现有事件
3. **实时更新**: 前端通过 SSE 订阅事件,实时更新
4. **审计日志**: 所有事件都可以记录

**权衡**:
- ✅ 模块解耦
- ✅ 易于扩展
- ✅ 实时更新
- ❌ 调试困难 (事件流追踪)
- ❌ 可能出现事件风暴
- ❌ 事件顺序难以保证

**替代方案**:
- **直接调用**: 简单,但耦合度高
- **消息队列 (RabbitMQ, Kafka)**: 适合分布式,但对于单机过于复杂
- **观察者模式**: 类似事件驱动,但缺少标准化

**依据**: `packages/opencode/src/bus/bus.ts`

---

### 决策 3: 采用 Instance Context 模式

**理由**:
1. **多项目支持**: 每个项目有独立的上下文
2. **资源隔离**: 避免项目间资源冲突
3. **生命周期管理**: 自动清理资源
4. **依赖注入**: 通过 Context 注入依赖

**权衡**:
- ✅ 多项目支持
- ✅ 资源隔离
- ✅ 生命周期管理
- ❌ 增加了抽象层
- ❌ 可能导致内存泄漏 (如果清理不当)

**替代方案**:
- **全局单例**: 简单,但无法支持多项目
- **依赖注入容器 (InversifyJS)**: 功能强大,但过于复杂
- **React Context**: 仅适用于 React,无法用于后端

**依据**: `packages/opencode/src/project/instance.ts`
