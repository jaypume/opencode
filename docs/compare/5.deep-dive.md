## 0. ID 体系说明

### 问题
OpenCode 中的 `sessionID`、`requestID`、`callID`、`messageID` 等各种 ID 的区别和联系是什么?

### 回答

OpenCode 采用了清晰的 ID 命名体系来标识不同层级的实体。所有 ID 都使用前缀模式，便于识别类型。

#### 0.1 核心 ID 类型

##### sessionID (会话 ID)
- **前缀**: `ses.*` (例如: `ses_abc123`)
- **作用域**: 整个对话会话
- **生命周期**: 从会话创建到删除/归档
- **用途**: 
  - 标识一个完整的对话会话
  - 关联该会话下的所有消息、工具调用、权限请求等
  - Session 可以 fork 产生子 Session
- **API 示例**:
  ```yaml
  /session/{sessionID}           # 获取会话详情
  /session/{sessionID}/message   # 获取会话的消息列表
  /session/{sessionID}/children  # 获取子会话
  ```

##### messageID (消息 ID)
- **前缀**: `msg.*` (例如: `msg_xyz789`)
- **作用域**: 单条消息
- **生命周期**: 消息创建后永久存在(除非删除)
- **用途**:
  - 标识用户消息或 AI 助手消息
  - 每条消息包含多个 Parts (文本、工具调用、工具输出等)
  - 支持消息级别的 fork 操作
- **关系**: `Message` 属于某个 `Session`
  ```typescript
  Message {
    id: string           // messageID
    sessionID: string    // 所属会话
    role: "user" | "assistant"
    parts: MessagePart[] // 消息的各个部分
  }
  ```

##### callID (工具调用 ID)
- **前缀**: 通常为工具调用的唯一标识符
- **作用域**: 单次工具调用
- **生命周期**: 工具调用开始到结束
- **用途**:
  - 标识 AI 发起的一次工具调用
  - 关联工具的输入参数和输出结果
  - 用于跟踪工具执行状态和结果
- **关系**: `callID` 关联到 `messageID` 和 `sessionID`
  ```typescript
  ToolCallPart {
    type: "tool"
    callID: string       // 工具调用 ID
    tool: string         // 工具名称
    state: "pending" | "running" | "success" | "error"
    input: object        // 工具输入参数
    output?: object      // 工具输出结果
  }
  ```

##### requestID (请求 ID)
- **前缀**: 
  - `per.*` - 权限请求 (Permission Request)
  - `que.*` - 问题请求 (Question Request)
- **作用域**: 单次交互请求
- **生命周期**: 请求创建到用户回复
- **用途**:
  - 标识需要用户确认的权限请求
  - 标识需要用户回答的问题
  - 关联请求和用户的回复
- **类型**:

  **PermissionRequest** (权限请求):
  ```typescript
  PermissionRequest {
    id: string           // requestID (per.*)
    sessionID: string    // 所属会话
    permission: string   // 权限类型 (如 "file:write")
    patterns: string[]   // 权限作用的文件模式
    metadata: object     // 额外元数据
    always: string[]     // 已授予的永久权限
    tool?: {
      messageID: string  // 触发权限请求的消息
      callID: string     // 触发权限请求的工具调用
    }
  }
  ```

  **QuestionRequest** (问题请求):
  ```typescript
  QuestionRequest {
    id: string           // requestID (que.*)
    sessionID: string    // 所属会话
    questions: QuestionInfo[]  // 问题列表
    tool?: {
      messageID: string  // 触发问题的消息
      callID: string     // 触发问题的工具调用
    }
  }
  ```

- **API 示例**:
  ```yaml
  /permission/{requestID}/reply  # 回复权限请求
  /question/{requestID}/reply    # 回复问题请求
  ```

#### 0.2 其他 ID 类型

##### ptyID (伪终端 ID)
- **前缀**: `pty.*`
- **用途**: 标识一个伪终端实例

##### partID (消息部分 ID)
- **用途**: 标识消息的某个部分 (文本、工具调用、工具输出等)

#### 0.3 ID 层级关系

```
Project (directory)
  └── Session (sessionID: ses.*)
      ├── Message (messageID: msg.*)
      │   └── MessagePart (partID)
      │       ├── TextPart
      │       ├── ToolCallPart (callID)
      │       └── ToolOutputPart (callID)
      ├── PermissionRequest (requestID: per.*)
      │   └── tool: { messageID, callID }
      └── QuestionRequest (requestID: que.*)
          └── tool: { messageID, callID }
```

#### 0.4 典型交互流程

**工具调用触发权限请求**:
```typescript
// 1. AI 在消息中调用工具
Message {
  id: "msg_001",
  sessionID: "ses_abc",
  role: "assistant",
  parts: [
    {
      type: "tool",
      callID: "call_123",
      tool: "StrReplace",
      state: "pending",
      input: { path: "/path/to/file.ts", ... }
    }
  ]
}

// 2. 工具执行需要权限,创建权限请求
PermissionRequest {
  id: "per_456",
  sessionID: "ses_abc",
  permission: "file:write",
  patterns: ["/path/to/file.ts"],
  tool: {
    messageID: "msg_001",  // 关联到触发的消息
    callID: "call_123"     // 关联到触发的工具调用
  }
}

// 3. 用户回复权限请求
POST /permission/per_456/reply
{
  reply: "once" | "always" | "reject"
}

// 4. 工具继续执行或被拒绝
MessagePart {
  callID: "call_123",
  state: "success" | "error",
  output: { ... }
}
```

#### 0.5 设计优势

1. **类型安全**: 通过前缀可以快速识别 ID 类型
2. **关联清晰**: 通过 ID 可以追溯完整的调用链
3. **并发支持**: 每个实体有独立 ID,支持并发操作
4. **调试友好**: 日志和错误信息中可以清晰看到实体关系
5. **API 一致性**: RESTful API 路径使用统一的 ID 模式

## 1. KiloCode 上下文压缩触发时机

### 问题
KiloCode 在什么时机去触发压缩的?

### 回答

**KiloCode 采用混合触发机制**:

#### 1.1 自动触发(Auto Condensation)

**触发条件**:
```typescript
// 文件: kilocode/src/core/context-management/index.ts:293-295
if (autoCondenseContext) {
  const contextPercent = (100 * prevContextTokens) / contextWindow
  if (contextPercent >= effectiveThreshold || prevContextTokens > allowedTokens) {
    // 触发压缩
  }
}
```

**两个触发条件(满足任一即触发)**:
1. **百分比阈值**: `contextPercent >= effectiveThreshold`
   - 默认阈值: `autoCondenseContextPercent` (可配置)
   - 支持 Profile 级别的自定义阈值
   - 有效范围: `MIN_CONDENSE_THRESHOLD` 到 `MAX_CONDENSE_THRESHOLD`

2. **绝对 Token 限制**: `prevContextTokens > allowedTokens`
   - `allowedTokens = contextWindow * (1 - TOKEN_BUFFER_PERCENTAGE) - reservedTokens`
   - `TOKEN_BUFFER_PERCENTAGE = 0.1` (保留 10% 缓冲区)
   - `reservedTokens = maxTokens || ANTHROPIC_DEFAULT_MAX_TOKENS`

**计算公式**:
```typescript
// 当前上下文 Token 数
prevContextTokens = totalTokens + lastMessageTokens

// 可用 Token 数
allowedTokens = contextWindow * 0.9 - maxTokens

// 上下文占用百分比
contextPercent = (100 * prevContextTokens) / contextWindow
```

**示例**:
```
假设:
- contextWindow = 200,000
- maxTokens = 8,000
- autoCondenseContextPercent = 70%
- prevContextTokens = 145,000

计算:
- allowedTokens = 200,000 * 0.9 - 8,000 = 172,000
- contextPercent = (145,000 / 200,000) * 100 = 72.5%

结果: 72.5% >= 70%, 触发压缩!
```

#### 1.2 手动触发(Manual Condensation)

**触发方式**:
1. **AI 主动调用**: AI 可以调用 `condense` 工具
   ```typescript
   // 文件: kilocode/src/core/tools/kilocode/condenseTool.ts:6-62
   export const condenseTool = async (cline: Task, block: ToolUse, ...) => {
     // AI 主动请求压缩
     const context = block.params.message
     // 用户确认后执行压缩
     const summarizedMessages = await summarizeConversation(...)
     await cline.overwriteApiConversationHistory(summarizedMessages.messages)
   }
   ```

2. **用户手动触发**: 通过 UI 或 API 调用 `POST /tasks/{id}/condense`

#### 1.3 压缩流程

**步骤**:
1. **检测溢出**: 在每次 API 调用前检查 Token 数
2. **尝试压缩**: 调用 `summarizeConversation()` 生成摘要
3. **失败回退**: 如果压缩失败,回退到滑动窗口截断(Sliding Window Truncation)

**压缩策略**:
```typescript
// 文件: kilocode/src/core/context-management/index.ts:296-314
const result = await summarizeConversation(
  messages,
  apiHandler,
  systemPrompt,
  taskId,
  prevContextTokens,
  true, // automatic trigger
  customCondensingPrompt,
  condensingApiHandler,
  useNativeTools,
)
```

**滑动窗口截断(Fallback)**:
```typescript
// 文件: kilocode/src/core/context-management/index.ts:318-338
if (prevContextTokens > allowedTokens) {
  const truncationResult = truncateConversation(messages, 0.5, taskId)
  // 隐藏 50% 的消息(标记为 truncationParent)
  // 插入截断标记(truncationMarker)
}
```

#### 1.4 与 OpenCode 的对比

| 维度 | KiloCode | OpenCode |
|------|----------|----------|
| 触发时机 | 每次 API 调用前检查 | 每个 `finish-step` 后检查 |
| 触发条件 | 百分比阈值 OR 绝对限制 | 自动检测溢出 |
| 用户控制 | 可手动触发 + AI 可调用工具 | 完全自动 |
| 失败回退 | 滑动窗口截断 | 无(依赖 Prune) |
| 压缩后继续 | 需要重新发送消息 | 自动创建 "Continue" 消息 |

**OpenCode 的压缩流程详解**:

```typescript
// 文件: opencode/packages/opencode/src/session/compaction.ts:92-193

// 1. 检测溢出
if (await SessionCompaction.isOverflow({ tokens, model })) {
  needsCompaction = true
}

// 2. 创建 CompactionPart
await SessionCompaction.create({
  sessionID,
  agent: "compaction",
  model: { providerID, modelID },
  auto: true,  // 自动继续
})

// 3. 使用 compaction Agent 生成摘要
const agent = await Agent.get("compaction")
const prompt = "Provide a detailed prompt for continuing our conversation above..."

// 4. AI 生成摘要(不提供工具)
await processor.process({
  messages: [...allMessages, { role: "user", content: [{ type: "text", text: prompt }] }],
  tools: {},  // 不提供工具
  agent: compactionAgent,
})

// 5. 自动创建 Continue 消息(如果 auto=true)
if (auto) {
  await Session.updatePart({
    type: "text",
    text: "Continue if you have next steps",
    synthetic: true,  // 标记为合成消息
  })
}

// 6. Prune 旧工具输出
await SessionCompaction.prune({ sessionID })
// 保留最近 40K tokens,标记更早的为 compacted
```

**Prune 策略**:
```typescript
const PRUNE_PROTECT = 40_000  // 保护最近 40K tokens
const PRUNE_MINIMUM = 20_000  // 至少压缩 20K tokens
const PRUNE_PROTECTED_TOOLS = ["skill"]  // 受保护的工具

// 从后往前扫描,标记旧工具输出
for (const part of message.parts.reverse()) {
  if (part.type === "tool" && !part.state.time.compacted) {
    const estimate = Token.estimate(part.state.output)
    if (total > PRUNE_PROTECT) {
      part.state.time.compacted = Date.now()
    }
  }
}
```

**关键差异**:
- **KiloCode**: 更灵活,支持手动控制和 AI 主动触发,失败时截断
- **OpenCode**: 更自动化,完全透明对用户,通过 Prune 保留输出但不发送给 AI

## 2. KiloCode 权限管理实现

### 问题
KiloCode 中是如何实现权限管理的?

### 回答

**KiloCode 没有内置的细粒度权限管理系统**。

#### 2.1 权限管理缺失

**证据**:
1. **无权限规则定义**: 在 Task 数据模型中没有 `permission` 字段
2. **无权限检查机制**: 工具执行时没有 `ctx.ask()` 调用
3. **无权限响应接口**: 没有类似 `/permission/{id}/respond` 的端点

**对比 OpenCode**:
```typescript
// OpenCode 有完整的权限系统
export namespace PermissionNext {
  export type Rule = {
    permission: string  // bash, edit, external_directory
    pattern: string     // 匹配模式(支持通配符)
    action: "allow" | "deny" | "ask"
  }
  
  export async function ask(input: Request): Promise<void> {
    // 评估规则
    const rule = evaluate(permission, pattern, rulesets)
    if (rule.action === "ask") {
      // 发布权限请求事件
      await Bus.publish(PermissionAsked, request)
      // 等待用户响应
    }
  }
}
```

#### 2.2 KiloCode 的"权限"机制

**实际上是工具可见性控制**:

1. **工具启用/禁用**:
   ```typescript
   // 通过配置控制工具是否可用
   {
     "tools": {
       "bash": true,    // 启用
       "edit": false    // 禁用
     }
   }
   ```

2. **用户确认机制**:
   - 某些工具执行前会请求用户确认
   - 但这是工具级别的实现,不是统一的权限系统
   - 例如: `condenseTool` 会调用 `cline.ask()` 请求用户确认

3. **API Key 管理**:
   - 通过 Profile 管理不同的 API Key
   - 控制哪些模型可以使用

#### 2.3 为什么 KiloCode 不需要复杂权限?

**设计理念差异**:

| 维度 | KiloCode | OpenCode |
|------|----------|----------|
| 运行环境 | VSCode 扩展(受限环境) | 独立 CLI/Server(完全访问) |
| 安全模型 | 依赖 VSCode 沙箱 | 需要自己实现安全控制 |
| 用户交互 | 同步 UI 交互 | 异步 SSE 事件 |
| 工具范围 | 有限的文件操作 | 完整的系统访问(bash, external_directory) |

**KiloCode 的安全策略**:
1. **环境隔离**: 运行在 VSCode 扩展沙箱中
2. **API 限制**: 只能通过 VSCode API 访问文件系统
3. **用户可见**: 所有操作在 UI 中可见,用户可随时中止

**OpenCode 的安全需求**:
1. **完整系统访问**: 可以执行任意 bash 命令
2. **外部目录访问**: 可能访问项目外的文件
3. **后台运行**: 可能在用户不注意时执行危险操作

#### 2.4 如果要为 KiloCode 添加权限管理

**建议方案**:

```typescript
// 1. 扩展 Task 数据模型
interface Task {
  permission?: {
    bash: {
      allowed: string[]  // ["npm*", "git*"]
      denied: string[]   // ["rm -rf*"]
    }
    edit: {
      allowed: string[]  // ["src/**"]
      denied: string[]   // [".env"]
    }
  }
}

// 2. 在工具执行前检查
async function executeTool(tool: string, params: any) {
  const allowed = checkPermission(task.permission, tool, params)
  if (!allowed) {
    throw new PermissionDeniedError()
  }
  // 执行工具
}

// 3. 提供权限配置 UI
// 在 VSCode 设置中添加权限规则配置
```

## 3. 事件系统(Bus)的角色

### 问题
Event 事件系统在整个系统中扮演了什么角色?

### 回答

**事件系统是 OpenCode 的神经中枢,负责解耦各模块并实现实时通信**。

#### 3.1 核心架构

**Bus 模块设计**:
```typescript
// 文件: opencode/packages/opencode/src/bus/index.ts
export namespace Bus {
  // 发布事件
  export async function publish<Definition>(
    def: Definition,
    properties: z.output<Definition["properties"]>,
  ) {
    const payload = { type: def.type, properties }
    
    // 1. 通知本地订阅者
    for (const sub of subscriptions.get(def.type) ?? []) {
      await sub(payload)
    }
    
    // 2. 通知全局订阅者(跨实例)
    GlobalBus.emit("event", {
      directory: Instance.directory,
      payload,
    })
  }
  
  // 订阅事件
  export function subscribe<Definition>(
    def: Definition,
    callback: (event) => void,
  ) {
    subscriptions.get(def.type).push(callback)
    return unsubscribe  // 返回取消订阅函数
  }
}
```

#### 3.2 事件系统的五大角色

##### 角色 1: 模块解耦

**问题**: 如何让文件编辑通知其他模块?

**解决方案**: 通过事件解耦
```typescript
// 文件: opencode/packages/opencode/src/tool/edit.ts:63-65
await Bun.write(filePath, params.newString)
await Bus.publish(File.Event.Edited, {
  file: filePath,
})
```

**订阅者**:
- **FileTime**: 更新文件访问时间缓存
- **Snapshot**: 触发快照更新
- **LSP**: 通知语言服务器文件变更
- **UI**: 更新文件树显示

**好处**:
- `edit` 工具不需要知道谁关心文件变更
- 新模块可以随时订阅事件,无需修改现有代码

##### 角色 2: 实时 UI 更新

**问题**: 如何实时推送 AI 生成的内容到客户端?

**解决方案**: SSE + 事件总线
```typescript
// 1. 工具执行时发布事件
// 文件: opencode/packages/opencode/src/session/processor.ts
Bus.publish(MessageV2.Event.PartUpdated, {
  part: toolPart,  // 工具调用状态
  delta: "..."     // 文本增量
})

// 2. HTTP Server 订阅事件并推送
// 文件: opencode/packages/opencode/src/server/server.ts
Bus.subscribeAll((event) => {
  // 通过 SSE 推送到所有连接的客户端
  for (const client of sseClients) {
    client.send(event)
  }
})

// 3. 客户端接收并更新 UI
sdk.session.prompt({...}).on("message.part.updated", (evt) => {
  // 更新 UI 显示工具执行进度
  updateToolStatus(evt.part)
})
```

**实时性**:
- 文本生成: 逐字推送(text-delta)
- 工具执行: 状态变更立即推送(running → completed)
- 权限请求: 实时弹出确认对话框

##### 角色 3: 跨会话协调

**问题**: 如何让多个 Session 共享资源?

**解决方案**: 全局事件总线
```typescript
// 文件: opencode/packages/opencode/src/tool/task.ts:111-114
const unsub = Bus.subscribe(MessageV2.Event.PartUpdated, async (evt) => {
  // 监听其他 Session 的工具执行状态
  if (evt.properties.part.sessionID !== session.id) return
  if (evt.properties.part.type !== "tool") return
  
  // 更新本 Session 的任务状态
  parts[evt.properties.part.callID] = {
    id: evt.properties.part.id,
    tool: evt.properties.part.tool,
    state: evt.properties.part.state,
  }
})
```

  return streamSSE(c, async (stream) => {
    // 1. 发送连接成功事件
    stream.writeSSE({
      data: JSON.stringify({
        type: "server.connected",
        properties: {},
      }),

      if (event.type === Bus.InstanceDisposed.type) {
        stream.close()
      }
    })
    
    // 3. 发送心跳(防止超时)
    const heartbeat = setInterval(() => {
      stream.writeSSE({
        data: JSON.stringify({
          type: "server.heartbeat",
          properties: {},
        }),
      })
    }, 30000)  // 每 30 秒
    
    // 4. 清理
    await new Promise<void>((resolve) => {
      stream.onAbort(() => {
        clearInterval(heartbeat)
        unsub()
        resolve()
      })
    })
  })

#### 3.5 性能优化

**问题**: 大量事件会不会影响性能?

**优化策略**:

1. **异步处理**: 所有事件处理都是异步的
   ```typescript
   const pending = []
   for (const sub of subscriptions) {
     pending.push(sub(payload))  // 不等待
   }
   await Promise.all(pending)  // 并行执行
   ```

2. **事件过滤**: 订阅者可以过滤不关心的事件
   ```typescript
   Bus.subscribe(MessageV2.Event.PartUpdated, (evt) => {
     if (evt.properties.part.sessionID !== mySessionID) return
     // 只处理自己的 Session
   })
   ```

3. **取消订阅**: 及时清理不再需要的订阅
   ```typescript
   const unsub = Bus.subscribe(...)
   // 使用完后取消订阅
   unsub()
   ```

4. **批量事件**: 合并多个小事件
   ```typescript
   // 不好: 每个字符发一个事件
   for (const char of text) {
     Bus.publish(TextDelta, { delta: char })
   }
   
   // 好: 批量发送
   Bus.publish(TextDelta, { delta: text })
   ```

## 4. 快照(Snapshot)和回滚(Revert)实现

### 问题
支持回滚和快照是如何实现的?

### 回答

**OpenCode 使用 Git 作为底层快照引擎,实现了非破坏性的文件版本管理**。

#### 4.1 核心设计

**独立的 Git 仓库**:
```typescript
// 文件: opencode/packages/opencode/src/snapshot/index.ts:29-30
function gitdir() {
  return path.join(Global.Path.data, "snapshot", Instance.project.id)
}
```

**目录结构**:
```
~/.opencode/data/snapshot/
  └── {projectID}/           # 每个项目一个独立的 Git 仓库
      ├── objects/           # Git 对象存储
      ├── refs/              # Git 引用
      └── config             # Git 配置
```

**为什么不用项目自己的 Git?**
1. **避免污染**: 不影响用户的 Git 历史
2. **独立管理**: 可以有不同的 GC 策略
3. **跨项目**: 支持非 Git 项目

#### 4.2 快照创建(Snapshot.track)

**触发时机**:
1. **每个 step 开始前**: 在 `step-start` 事件中创建
2. **每个 step 结束后**: 在 `finish-step` 事件中创建
3. **用户手动触发**: 通过 API 调用

**代码证据**:
```typescript
// 文件: opencode/packages/opencode/src/session/processor.ts:225-234
case "step-start":
  snapshot = await Snapshot.track()  // 创建快照
  await Session.updatePart({
    id: Identifier.ascending("part"),
    messageID: input.assistantMessage.id,
    sessionID: input.sessionID,
    snapshot,
    type: "step-start",
  })
  break

// 文件: opencode/packages/opencode/src/session/processor.ts:248-249
case "finish-step":
  await Session.updatePart({
    ...
    snapshot: await Snapshot.track(),  // 再次创建快照
    type: "step-finish",
  })
```

**实现**:
```typescript
// 文件: opencode/packages/opencode/src/snapshot/index.ts:50-76
export async function track() {
  const git = gitdir()
  
  // 1. 初始化 Git 仓库(如果不存在)
  if (await fs.mkdir(git, { recursive: true })) {
    await $`git init`.env({
      GIT_DIR: git,
      GIT_WORK_TREE: Instance.worktree,
    })
    // 禁用换行符转换(Windows 兼容)
    await $`git config core.autocrlf false`
  }
  
  // 2. 添加所有文件到暂存区
  await $`git add .`
  
  // 3. 创建 Git tree 对象(不创建 commit)
  const hash = await $`git write-tree`.text()
  
  return hash.trim()  // 返回 tree hash
}
```

**关键点**:
- **只创建 tree,不创建 commit**: 更轻量,避免 commit 历史膨胀
- **tree hash 是快照标识**: 例如 `a1b2c3d4...`
- **增量存储**: Git 自动去重,相同文件只存储一次

#### 4.3 快照对比(Snapshot.patch)

**获取文件变更列表**:
```typescript

export async function patch(hash: string): Promise<Patch> {
  const git = gitdir()
  
  // 1. 添加当前文件到暂存区
  await $`git add .`
  
  // 2. 对比快照和当前状态
  const result = await $`git diff --name-only ${hash} -- .`
  
  // 3. 解析变更的文件列表
  const files = result.text()
    .trim()
    .split("\n")
    .map(x => path.join(Instance.worktree, x))
  
  return { hash, files }
}
```

**Patch 数据结构**:
```typescript

  ]
}

#### 4.4 回滚(Revert)实现

**回滚流程**:
```typescript
// 文件: opencode/packages/opencode/src/session/revert.ts:22-65
export async function revert(input: RevertInput) {
  // 1. 获取所有消息
  const all = await Session.messages({ sessionID: input.sessionID })
  
  // 2. 找到回滚点
  let revert: Session.Info["revert"]
  const patches: Snapshot.Patch[] = []
  
  for (const msg of all) {
    for (const part of msg.parts) {
      if (revert) {
        // 收集回滚点之后的所有 patch
        if (part.type === "patch") {
          patches.push(part)
        }
        continue
      }
      
      // 找到回滚目标
      if (msg.info.id === input.messageID || part.id === input.partID) {
        revert = {
          messageID: msg.info.id,
          partID: input.partID,
        }
      }
    }
  }
  
  // 3. 创建当前快照(用于 unrevert)
  revert.snapshot = await Snapshot.track()
  
  // 4. 执行回滚
  await Snapshot.revert(patches)
  
  // 5. 生成 diff(用于 UI 显示)
  if (revert.snapshot) {
    revert.diff = await Snapshot.diff(revert.snapshot)
  }
  
  // 6. 更新 Session 状态
  return Session.update(input.sessionID, (draft) => {
    draft.revert = revert
  })
}
```

**Snapshot.revert 实现**:
```typescript
// 文件: opencode/packages/opencode/src/snapshot/index.ts:130-160
export async function revert(patches: Patch[]) {
  const files = new Set<string>()
  const git = gitdir()
  
  for (const item of patches) {
    for (const file of item.files) {
      if (files.has(file)) continue  // 避免重复处理
      
      // 从快照恢复文件
      const result = await $`git checkout ${item.hash} -- ${file}`
      
      if (result.exitCode !== 0) {
        // 检查文件是否在快照中存在
        const checkTree = await $`git ls-tree ${item.hash} -- ${file}`
        
        if (checkTree.text().trim()) {
          // 文件存在但 checkout 失败,保留当前版本
          log.info("file existed but checkout failed, keeping")
        } else {
          // 文件在快照中不存在,删除
          log.info("file did not exist in snapshot, deleting")
          await fs.unlink(file).catch(() => {})
        }
      }
      
      files.add(file)
    }
  }
}
```

**回滚逻辑**:
1. **收集 Patches**: 从回滚点到当前的所有文件变更
2. **逆向应用**: 按照 patch 顺序恢复文件
3. **处理删除**: 如果文件在快照中不存在,则删除
4. **处理冲突**: 如果恢复失败,保留当前版本

#### 4.5 取消回滚(Unrevert)

**实现**:
```typescript
// 文件: opencode/packages/opencode/src/session/revert.ts:67-77
export async function unrevert(input: { sessionID: string }) {
  const session = await Session.get(input.sessionID)
  if (!session.revert) return session
  
  // 恢复到回滚前的快照
  if (session.revert.snapshot) {
    await Snapshot.restore(session.revert.snapshot)
  }
  
  // 清除回滚状态
  return Session.update(input.sessionID, (draft) => {
    draft.revert = undefined
  })
}
```

}

#### 4.8 与传统 Git 的对比

| 维度 | 传统 Git | OpenCode Snapshot |
|------|----------|-------------------|
| 存储位置 | 项目 `.git/` | `~/.opencode/data/snapshot/{projectID}/` |
| 提交对象 | commit | tree (无 commit) |
| 历史记录 | 完整 commit 历史 | 仅保留 tree hash |
| 清理策略 | 手动 `git gc` | 自动清理 7 天前的对象 |
| 用途 | 版本控制 | AI 操作的撤销/重做 |
| 性能 | 较慢(需要创建 commit) | 较快(仅创建 tree) |

#### 4.9 优势和局限

**优势**:
1. **轻量**: 只存储 tree,不创建 commit
2. **增量**: Git 自动去重,节省空间
3. **可靠**: 基于成熟的 Git 技术
4. **灵活**: 支持部分回滚(回滚到某个 Part)

**局限**:
1. **仅支持 Git 项目**: 非 Git 项目需要额外处理
2. **无法回滚删除的文件**: 如果文件被永久删除,无法恢复
3. **性能开销**: 大项目的 `git add .` 可能较慢

**改进建议**:
1. **增量快照**: 只跟踪变更的文件,而不是整个项目
2. **压缩存储**: 使用 Git 的 pack 格式压缩存储
3. **异步清理**: 在后台线程执行清理,避免阻塞主线程

#### 5.9 Agent 的完整调用链

**场景**: 用户发送消息,使用 build Agent

```
1. 用户发送消息
   POST /session/ses_123/message
   { "agent": "build", "parts": [{ "type": "text", "text": "Fix bug" }] }
   
2. HTTP 路由处理
   → packages/opencode/src/server/routes/session.ts
   → SessionPrompt.prompt()
   
3. 获取 Agent 配置
   → packages/opencode/src/agent/agent.ts
   → Agent.get("build")
   → 返回 Agent.Info { permission, prompt, model, ... }
   
4. 合并权限规则
   → Agent.permission (Agent 级别)
   → Session.permission (Session 级别)
   → PermissionNext.merge(...)
   
5. 构建系统提示
   → SystemPrompt.build({
       agent: agentInfo,
       session: sessionInfo,
       project: projectInfo,
     })
   → 合并: Agent.prompt + 项目规则 + 用户指令
   
6. 解析工具列表
   → resolveTools()
   → 根据 Agent.permission 过滤工具
   → 只提供 Agent 有权限使用的工具
   
7. 调用 LLM
   → LLM.stream({
       model: agent.model || session.model,
       messages: [...],
       tools: filteredTools,
       temperature: agent.temperature,
       topP: agent.topP,
     })
   
8. AI 决定调用工具
   → 检查工具权限
   → PermissionNext.ask({ permission: "bash", ... })
   → 评估 Agent.permission 和 Session.permission
   
9. 工具执行
   → tool.execute(args, ctx)
   → 根据 Agent.permission 决定是否需要用户确认
```

**关键代码**:
```typescript
// 文件: opencode/packages/opencode/src/session/prompt.ts:643-822
async function resolveTools() {
  const agent = await Agent.get(input.agent)
  const tools = {}
  
  // 获取所有工具
  const allTools = {
    ...ToolRegistry.tools(),
    ...await MCP.tools(),
  }
  
  // 根据 Agent 权限过滤
  for (const [name, tool] of Object.entries(allTools)) {
    const rule = PermissionNext.evaluate("tool", name, agent.permission)
    if (rule.action !== "deny") {
      tools[name] = tool
    }
  }
  
  return tools
}
```

## 6. PTY vs TUI

### 问题
TUI 和 PTY 有什么区别? 为什么要弄 2 个接口?

### 回答

**PTY 和 TUI 是两个不同层次的抽象,服务于不同的用例**。

#### 6.1 PTY (Pseudo-Terminal)

**定义**: 伪终端,提供底层的终端会话管理。

**核心功能**:
```typescript
// 文件: opencode/packages/opencode/src/pty/index.ts
export namespace Pty {
  export type Info = {
    id: string          // PTY ID
    title?: string      // 标题
    cwd: string         // 工作目录
    command: string     // 命令
    args: string[]      // 参数
    env: Record<string, string>  // 环境变量
    size: {             // 终端大小
      rows: number
      cols: number
    }
    pid?: number        // 进程 ID
    exitCode?: number   // 退出码
  }
  
  // 创建 PTY
  export async function create(input: CreateInput): Promise<Info>
  
  // 连接 PTY (WebSocket)
  export function connect(ptyID: string): WebSocket
  
  // 写入数据
  export function write(ptyID: string, data: string): void
  
  // 调整大小
  export function resize(ptyID: string, size: { rows: number; cols: number }): void
}
```

**用途**:
1. **运行长时间命令**: 例如 `npm run dev`, `docker logs -f`
2. **交互式程序**: 例如 `vim`, `htop`, `python REPL`
3. **终端仿真**: 在 Web UI 中嵌入终端

**API 示例**:
```typescript
// 1. 创建 PTY
POST /pty
{
  "command": "bash",
  "cwd": "/path/to/project",
  "env": { "NODE_ENV": "development" }
}
// Response: { id: "pty_123", ... }

// 2. 连接 PTY (WebSocket)
ws://localhost:4096/pty/pty_123/connect

// 3. 发送命令
WebSocket.send("npm run dev\n")

// 4. 接收输出
WebSocket.onmessage = (evt) => {
  console.log(evt.data)  // 终端输出
}

// 5. 调整大小
PUT /pty/pty_123
{
  "size": { "rows": 40, "cols": 120 }
}

// 6. 终止 PTY
DELETE /pty/pty_123
```

**特点**:
- **低级 API**: 直接操作终端会话
- **完全控制**: 可以发送任意输入,接收原始输出
- **持久化**: PTY 会话独立于 Session 存在
- **多客户端**: 多个客户端可以连接同一个 PTY

#### 6.2 TUI (Terminal User Interface)

**定义**: 终端用户界面,提供高级的 CLI 交互抽象。

**核心功能**:
```typescript
// 文件: opencode/packages/opencode/src/server/routes/tui.ts
export namespace TuiEvent {
  // 追加提示
  export const PromptAppend = BusEvent.define(
    "tui.prompt.append",
    z.object({
      sessionID: z.string(),
      content: z.string(),
    })
  )
  
  // 追加工具结果
  export const ToolResultAppend = BusEvent.define(
    "tui.tool.result.append",
    z.object({
      sessionID: z.string(),
      tool: z.string(),
      result: z.string(),
    })
  )
  
  // 更新状态
  export const StatusUpdate = BusEvent.define(
    "tui.status.update",
    z.object({
      sessionID: z.string(),
      status: z.enum(["idle", "thinking", "executing"]),
    })
  )
}
```

**用途**:
1. **CLI 工具集成**: 让 CLI 工具能够控制 OpenCode
2. **双向通信**: CLI 可以发送请求,OpenCode 可以推送事件
3. **UI 抽象**: 提供比 PTY 更高级的 UI 控制

**API 示例**:
```typescript
// 1. CLI 工具订阅 TUI 事件
GET /tui/control/next
// 阻塞等待下一个 TUI 请求

// 2. OpenCode 发送 TUI 请求
POST /tui/append-prompt
{
  "sessionID": "ses_123",
  "content": "Please review this code"
}

// 3. CLI 工具接收请求
{
  "path": "/tui/append-prompt",
  "body": {
    "sessionID": "ses_123",
    "content": "Please review this code"
  }
}

// 4. CLI 工具处理请求并响应
POST /tui/control/response
{
  "success": true
}

// 5. OpenCode 接收响应并继续
```

**特点**:
- **高级 API**: 抽象了终端的复杂性
- **事件驱动**: 基于事件总线
- **双向通信**: 请求-响应模式
- **UI 控制**: 可以控制 CLI 工具的 UI 显示

#### 6.3 核心差异

| 维度 | PTY | TUI |
|------|-----|-----|
| **抽象层次** | 低级(终端会话) | 高级(UI 控制) |
| **通信方式** | WebSocket(双向流) | HTTP + 事件总线 |
| **数据格式** | 原始字节流 | 结构化 JSON |
| **生命周期** | 独立(可长期存在) | 绑定到请求-响应 |
| **用途** | 运行命令,交互式程序 | CLI 工具集成 |
| **控制粒度** | 字符级别 | 事件级别 |
| **状态管理** | 无状态(纯终端) | 有状态(Session 绑定) |

        }

#### 6.5 架构设计

**PTY 架构**:
```
Client (Web/CLI)
  ↓ WebSocket
PTY Manager
  ↓ node-pty
OS Pseudo-Terminal
  ↓ fork/exec
Shell Process (bash/zsh)
```

**TUI 架构**:
```
OpenCode Server
  ↓ HTTP POST /tui/append-prompt
TUI Request Queue
  ↓ HTTP GET /tui/control/next
CLI Tool (opencode-cli)
  ↓ Process & Display
User Terminal
  ↓ HTTP POST /tui/control/response
TUI Response Queue
  ↓ Return to OpenCode
OpenCode Server (continue)
```

#### 6.6 为什么需要两个接口?

**设计原因**:

1. **不同的抽象层次**:
   - PTY: 底层终端会话,用于运行命令
   - TUI: 高层 UI 控制,用于集成 CLI 工具

2. **不同的通信模式**:
   - PTY: 持续的双向流(WebSocket)
   - TUI: 请求-响应模式(HTTP + 事件)

3. **不同的用例**:
   - PTY: 嵌入终端、运行长时间命令
   - TUI: CLI 工具集成、UI 控制

4. **职责分离**:
   - PTY: 专注于终端会话管理
   - TUI: 专注于 CLI 工具通信

**类比**:
- **PTY** 像 `docker exec -it`: 直接进入容器的终端
- **TUI** 像 `docker API`: 通过 API 控制容器

## 7. Skill 功能实现

### 问题
Skill 功能是如何实现的? 如果要开发框架实现 Skill 需要按照什么流程?

### 回答

**Skill 是 OpenCode 的"知识库系统",通过 Markdown 文件定义可复用的专业知识**。

#### 7.1 Skill 定义

**文件结构**:
```
.opencode/
  skill/
    react-patterns/
      SKILL.md          # Skill 定义文件
    api-design/
      SKILL.md
    testing-best-practices/
      SKILL.md
```

**SKILL.md 格式**:
```markdown
---
name: react-patterns
description: React best practices and common patterns
---

# React Patterns

## Component Composition

Use composition over inheritance...

## Hooks Best Practices

1. Always call hooks at the top level
2. Only call hooks from React functions
...

## Performance Optimization

Use React.memo for expensive components...
```

**Frontmatter 字段**:
- `name`: Skill 名称(必填)
- `description`: Skill 描述(必填)
- 其他字段: 可选的元数据

#### 7.2 Skill 加载机制

**扫描目录**:
```typescript
// 文件: opencode/packages/opencode/src/skill/skill.ts:42-124
export const state = Instance.state(async () => {
  const skills: Record<string, Info> = {}
  
  // 1. 扫描 .claude/skills/ 目录(兼容 Claude Code)
  const claudeDirs = await Array.fromAsync(
    Filesystem.up({
      targets: [".claude"],
      start: Instance.directory,
      stop: Instance.worktree,
    })
  )
  
  // 也包括全局 ~/.claude/skills/
  const globalClaude = `${Global.Path.home}/.claude`
  if (await Filesystem.isDir(globalClaude)) {
    claudeDirs.push(globalClaude)
  }
  
  // 扫描 .claude/skills/**/SKILL.md
  for (const dir of claudeDirs) {
    for await (const match of CLAUDE_SKILL_GLOB.scan({ cwd: dir })) {
      await addSkill(match)
    }
  }
  
  // 2. 扫描 .opencode/skill/ 目录
  for (const dir of await Config.directories()) {
    for await (const match of OPENCODE_SKILL_GLOB.scan({ cwd: dir })) {
      await addSkill(match)
    }
  }
  
  return skills
})
```

**加载优先级**:
1. 项目级别 `.opencode/skill/`
2. 项目级别 `.claude/skills/`
3. 全局 `~/.opencode/skill/`
4. 全局 `~/.claude/skills/`

**Glob 模式**:
```typescript
const OPENCODE_SKILL_GLOB = new Bun.Glob("{skill,skills}/**/SKILL.md")
const CLAUDE_SKILL_GLOB = new Bun.Glob("skills/**/SKILL.md")
```

**支持的路径**:
- `.opencode/skill/react-patterns/SKILL.md`
- `.opencode/skills/react-patterns/SKILL.md`
- `.claude/skills/react-patterns/SKILL.md`

**加载时机**:
- **启动时**: `Instance.state()` 初始化时加载
- **懒加载**: 使用 `Instance.state()` 实现懒加载和缓存
- **自动刷新**: 文件变更时自动重新加载(通过 Bus 事件)

#### 7.3 Skill 解析

**解析 Frontmatter**:

##### 用法 1: 框架特定模式(实际示例)

**场景**: OpenWork 的 SolidJS 响应式模式

```markdown
---
name: solidjs-patterns
description: SolidJS reactivity + UI state patterns for OpenWork
---

## Why this skill exists

OpenWork's UI is SolidJS: it updates via **signals**, not React-style rerenders.
Most "UI stuck" bugs are actually **state coupling** bugs (e.g. one global `busy()` 
disabling an unrelated action), not rerender issues.

## Core rules

- Prefer **fine-grained signals** over shared global flags.
- Keep async actions **scoped** (each action gets its own `pending` state).
- Derive UI state via `createMemo()` instead of duplicating booleans.

## Scoped async actions (recommended)

```ts
const [replying, setReplying] = createSignal(false);

async function respond() {
  if (replying()) return;
  setReplying(true);
  try {
    await doTheThing();
  } finally {
    setReplying(false);
  }
}
```

### Why

A single `busy()` boolean creates deadlocks:
- Long-running task sets `busy(true)`
- A permission prompt appears and its buttons are disabled by `busy()`
- The task can't continue until permission is answered
- The user can't answer because buttons are disabled

Fix: permission UI must be disabled only by a **permission-specific** pending state.
```

**实际文件**: `openwork/.opencode/skill/solidjs-patterns/SKILL.md`

**使用**:

async function scanSkills(directories: string[]): Promise<Skill[]> {
  const skills: Skill[] = []
  
  for (const dir of directories) {
    // 使用 glob 查找 SKILL.md 文件
    const files = await glob(`${dir}/**/SKILL.md`)
    
    for (const file of files) {
      const skill = await loadSkill(file)
      if (skill) skills.push(skill)
    }
  }

// 2. 加载单个 Skill
async function loadSkill(filepath: string): Promise<Skill | null> {
  try {
    // 读取文件
    const content = await fs.readFile(filepath, 'utf-8')
    
    // 解析 Frontmatter
    const { data, content: body } = matter(content)
    
    // 验证必填字段
    if (!data.name || !data.description) {
      console.warn(`Invalid skill: ${filepath}`)
      return null
    }
    
    return {
      name: data.name,
      description: data.description,
      content: body,
      location: filepath,
      tags: data.tags,
      version: data.version,
    }
  } catch (error) {
    console.error(`Failed to load skill: ${filepath}`, error)
    return null
  }
}
```

##### 步骤 3: 实现 Skill 注册表

```typescript
class SkillRegistry {
  private skills = new Map<string, Skill>()
  
  // 注册 Skill
  register(skill: Skill) {
    if (this.skills.has(skill.name)) {
      console.warn(`Duplicate skill: ${skill.name}`)
    }
    this.skills.set(skill.name, skill)
  }
  
  // 获取 Skill
  get(name: string): Skill | undefined {
    return this.skills.get(name)
  }
  
  // 列出所有 Skill
  list(): Skill[] {
    return Array.from(this.skills.values())
  }
  
  // 搜索 Skill
  search(query: string): Skill[] {
    return this.list().filter(skill =>
      skill.name.includes(query) ||
      skill.description.includes(query) ||
      skill.tags?.some(tag => tag.includes(query))
    )
  }
}
```

class FileLock {
  private locks = new Map<string, string>()  // file -> sessionID
  
  async acquire(file: string, sessionID: string): Promise<boolean> {
    if (this.locks.has(file)) {
      const owner = this.locks.get(file)
      if (owner !== sessionID) {
        return false  // 文件已被锁定
      }
    }
    this.locks.set(file, sessionID)
    return true
  }
  
  release(file: string, sessionID: string) {
    if (this.locks.get(file) === sessionID) {
      this.locks.delete(file)
    }
  }
}

### 8.6 Message 的 Parts 结构设计

**问题**: 为什么 OpenCode 要把 Message 拆分成 Parts?

**回答**:

**Parts 结构的优势**:

**1. 细粒度更新**:
```typescript
// 不好的设计: 整个消息作为一个单元
{
  id: "msg_123",
  content: "Let me check the file...\n[bash output]\n[file content]\nDone!"
}
// 问题: 无法单独更新某个部分

// 好的设计: 拆分成多个 Parts
{
  id: "msg_123",
  parts: [
    { id: "part_1", type: "text", text: "Let me check the file..." },
    { id: "part_2", type: "tool", tool: "bash", status: "running" },
    { id: "part_3", type: "tool", tool: "read", status: "pending" },
    { id: "part_4", type: "text", text: "Done!" },
  ]
}
// 优势: 可以单独更新 part_2 的状态
```

**2. 流式更新**:
```typescript
// 文件: opencode/packages/opencode/src/session/processor.ts:293-302
case "text-delta":
  if (currentText) {
    currentText.text += value.text  // 增量更新
    await Session.updatePart({
      part: currentText,
      delta: value.text,  // 只发送增量
    })
  }
  break
```

**UI 实时显示**:
```typescript

  }
})
```

**3. 独立的生命周期**:
```typescript
// 每个 Part 有独立的时间戳
{
  id: "part_2",
  type: "tool",
  tool: "bash",

    status: "completed",

}

**4. 选择性压缩**:
```typescript

**5. 灵活的回滚**:

**Part 类型完整列表**:

| Part 类型 | 用途 | 关键字段 |
|-----------|------|----------|
| **text** | AI 生成的文本内容 | `text`, `time`, `synthetic` |

**设计权衡**:
- **优点**: 细粒度控制、流式更新、选择性压缩

#### Request 与 Response 的对应关系

**Request → Response 流程**:

```
1. 用户发送 Request
   POST /session/ses_123/message
   { "parts": [{ "type": "text", "text": "Hello" }] }

2. 创建用户消息(User Message)
   { "info": { "role": "user", ... }, "parts": [{ "type": "text", "text": "Hello" }] }

3. AI 处理并生成 Response
   { "info": { "role": "assistant", ... }, "parts": [...] }

4. 返回 Response 给客户端
   { "info": {...}, "parts": [{ "type": "text", "text": "Hi!" }] }
```

**Request Parts vs Response Parts**:

| Part 类型 | Request | Response | 说明 |
|-----------|---------|----------|------|
| **text** | ✅ | ✅ | 双向 |
| **file** | ✅ | ✅ | 双向(用户上传,AI 生成) |
| **agent** | ✅ | ✅ | 双向(用户切换,AI 记录) |
| **subtask** | ✅ | ✅ | 双向(用户创建,AI 记录) |
| **tool** | ❌ | ✅ | 仅 Response(AI 调用工具) |
| **step-start** | ❌ | ✅ | 仅 Response(AI 步骤标记) |
| **step-finish** | ❌ | ✅ | 仅 Response(AI 步骤统计) |
| **reasoning** | ❌ | ✅ | 仅 Response(AI 推理过程) |
| **compaction** | ❌ | ✅ | 仅 Response(系统压缩标记) |
| **retry** | ❌ | ✅ | 仅 Response(系统重试标记) |
| **patch** | ❌ | ✅ | 仅 Response(系统变更记录) |
| **snapshot** | ❌ | ✅ | 仅 Response(系统快照标记) |

#### parts 数组详解

##### 1. step-start (步骤开始)

**用途**: 标记一个推理步骤的开始,同时创建快照用于回滚。

```typescript

**字段说明**:
- `snapshot`: 可选,Git tree hash,记录步骤开始前的文件状态
- 每个 assistant 消息通常以 `step-start` 开始

**使用场景**:
```typescript

→ step-start (创建快照)

→ text part

// 3. AI 调用工具
→ tool part

// 4. 步骤结束
→ step-finish (创建快照)

##### 2. text (文本内容)

**用途**: AI 生成的文本内容,逐字流式推送。

```typescript

  "id": "prt_xxx",
  "sessionID": "ses_xxx",
  "messageID": "msg_xxx",
  "type": "text",

**字段说明**:

#### Parts 的设计原则

**1. 原子性**: 每个 Part 是一个独立的、不可分割的单元
**2. 顺序性**: Parts 按时间顺序排列,反映执行流程
**3. 可追溯性**: 每个 Part 都有唯一 ID 和时间戳
**4. 可更新性**: Part 的状态可以独立更新(如 tool 的 status)
**5. 可压缩性**: 旧的 Part 可以被标记为已压缩,节省空间

### 8.6.3 Parts 系统的深度问答

#### 问题 1: Tool 的返回是流式更新的吗?

**回答**: **是的,Tool 通过 metadata 实现流式更新**。

##### 流式更新机制

**实现方式**:
```typescript
// 文件: opencode/packages/opencode/src/tool/bash.ts:170-189
async execute(params, ctx) {
  let output = ""
  
  // 1. 初始化 metadata
  ctx.metadata({
    metadata: {
      output: "",
      description: params.description,
    },
  })
  
  // 2. 监听 stdout,实时更新 metadata
  proc.stdout.on("data", (chunk) => {
    output += chunk.toString()
    
    // 流式更新 metadata(截断到 30KB)
    ctx.metadata({
      metadata: {
        output: output.slice(0, 30000) + (output.length > 30000 ? "\n\n..." : ""),
        description: params.description,
      },
    })
  })
  
  // 3. 命令执行完成,返回完整输出
  return {
    title: "Command executed",
    output: output,  // 完整输出,存储到数据库
    metadata: { exitCode: 0 }
  }
}
```

**流式更新流程**:

```
1. Tool 开始执行
   → ctx.metadata({ metadata: { output: "" } })
   → Bus.publish(PartUpdated, { part: { status: "running", metadata: { output: "" } } })
   → SSE 推送到前端
   → 前端显示"执行中..."

2. stdout 输出第一行
   → ctx.metadata({ metadata: { output: "line 1\n" } })
   → Bus.publish(PartUpdated)
   → SSE 推送
   → 前端更新显示"line 1"

3. stdout 输出第二行
   → ctx.metadata({ metadata: { output: "line 1\nline 2\n" } })
   → Bus.publish(PartUpdated)
   → SSE 推送
   → 前端更新显示"line 1\nline 2"

4. 命令执行完成
   → return { output: "line 1\nline 2\nline 3\n" }
   → Bus.publish(PartUpdated, { part: { status: "completed", output: "..." } })
   → SSE 推送
   → 前端显示"执行完成"
```

**关键点**:

1. **metadata 用于流式更新**: 
   - 在工具执行过程中,通过 `ctx.metadata()` 更新元数据
   - 元数据会立即通过 SSE 推送到前端
   - 前端可以实时显示工具的执行进度

2. **output 用于最终结果**:
   - 工具返回的 `output` 是完整的输出
   - 存储到数据库,供 AI 和后续查询使用
   - 不受 metadata 的 30KB 截断限制

3. **截断策略**:
   - metadata 中的 output 截断到 30KB,避免大量数据传输
   - 完整的 output 存储在数据库中
   - AI 读取的是完整的 output,不受截断影响

**其他支持流式更新的工具**:

| 工具 | 流式更新内容 | 更新频率 |
|------|-------------|----------|
| **bash** | stdout/stderr 输出 | 每次 data 事件 |
| **edit** | diff 预览 | 编辑完成时 |
| **task** | 子任务进度 | 子任务状态变更时 |
| **read** | 无流式更新 | 读取完成后一次性返回 |
| **grep** | 无流式更新 | 搜索完成后一次性返回 |

##### 不同 Part 类型的流式更新对比

| Part 类型 | 是否流式 | 更新方式 | 更新内容 |
|-----------|---------|---------|---------|
| **text** | ✅ 是 | delta 增量 | 逐字追加文本 |
| **tool** | ✅ 是 | metadata 更新 | 实时输出、状态变更 |
| **reasoning** | ✅ 是 | delta 增量 | 逐字追加推理过程 |
| **file** | ❌ 否 | 一次性 | 完整文件内容 |
| **step-start** | ❌ 否 | 一次性 | 快照 hash |
| **step-finish** | ❌ 否 | 一次性 | Token 统计 |

##### Parts 的转换:存储格式 vs AI 格式

**关键点**: **存储的 Parts 和发送给 AI 的 Parts 是不同的**。

###### 存储格式(Parts)

**用途**: 完整记录所有交互细节,供前端展示和历史查询

```typescript
// 存储在数据库中的 Parts
{
  "parts": [
    { "type": "step-start", "snapshot": "a1b2c3d4..." },
    { "type": "text", "text": "Let me check..." },
    { "type": "tool", "tool": "bash", "state": { "status": "completed", "output": "..." } },
    { "type": "step-finish", "tokens": {...} }
  ]
}
```

###### AI 格式(ModelMessage)

**用途**: 发送给 AI 的简化格式,符合 AI SDK 的要求

```typescript
// 转换后发送给 AI 的格式
// 文件: opencode/packages/opencode/src/session/message-v2.ts:500-580
export function toModelMessage(messages: WithParts[]): ModelMessage[] {
  const result: ModelMessage[] = []
  
  for (const msg of messages) {
    if (msg.info.role === "user") {
      // 用户消息:只保留 text 和 file
      result.push({
        role: "user",
        content: msg.parts
          .filter(p => p.type === "text" || p.type === "file")
          .map(p => {
            if (p.type === "text") {
              return { type: "text", text: p.text }
            }
            if (p.type === "file") {
              return { type: "image", image: p.url }
            }
          })
      })
    }
    
    if (msg.info.role === "assistant") {
      const content = []
      
      for (const part of msg.parts) {
        // step-start: 忽略(AI 不需要知道)
        if (part.type === "step-start") continue
        
        // text: 保留
        if (part.type === "text") {
          content.push({ type: "text", text: part.text })
        }
        
        // tool: 转换为 tool-result
        if (part.type === "tool" && part.state.status === "completed") {
          content.push({
            type: `tool-${part.tool}`,
            state: "output-available",
            toolCallId: part.callID,
            input: part.state.input,
            output: part.state.time.compacted 
              ? "[Old tool result content cleared]"  // 已压缩
              : part.state.output,  // 完整输出
          })
        }
        
        // step-finish: 忽略(AI 不需要知道 Token 统计)
        if (part.type === "step-finish") continue
      }
      
      result.push({ role: "assistant", content })
    }
  }
  
  return result
}
```

**转换示例**:

```typescript
// 存储格式(完整)
{
  "info": { "role": "assistant", ... },
  "parts": [
    { "type": "step-start", "snapshot": "abc123" },
    { "type": "text", "text": "Let me check..." },
    { "type": "tool", "callID": "call_1", "tool": "bash", "state": { 
      "status": "completed", 
      "input": { "command": "ls" },
      "output": "file1\nfile2" 
    }},
    { "type": "step-finish", "tokens": { "input": 100, "output": 20 } }
  ]
}

// 转换为 AI 格式(简化)
{
  "role": "assistant",
  "content": [
    { "type": "text", "text": "Let me check..." },
    { 
      "type": "tool-bash",
      "state": "output-available",
      "toolCallId": "call_1",
      "input": { "command": "ls" },
      "output": "file1\nfile2"
    }
  ]
}
```

**为什么要转换?**

1. **AI 不需要所有信息**: 
   - `step-start` / `step-finish`: AI 不需要知道步骤边界
   - `snapshot`: AI 不需要知道快照 hash
   - `tokens` / `cost`: AI 不需要知道 Token 统计

2. **符合 AI SDK 格式**:
   - AI SDK 要求特定的消息格式
   - 需要将 OpenCode 的 Part 格式转换为 AI SDK 的格式

3. **压缩优化**:
   - 已压缩的工具输出替换为 `[Old tool result content cleared]`
   - 节省 Token,降低成本

##### 设计权衡

**优点**:

1. **统一的数据格式**: 
   - 用户和 AI 使用相同的 Part 格式
   - 减少格式转换的复杂度
   - 便于扩展新的 Part 类型

2. **完整的历史记录**:
   - 存储所有交互细节
   - 支持回放和审计
   - 便于调试和分析

3. **灵活的展示**:
   - 前端可以选择性地展示不同的 Part
   - 支持折叠/展开
   - 支持自定义渲染

4. **双向通信**:
   - 用户可以发送 file Part(上传文件)
   - AI 可以返回 file Part(生成图片)
   - 支持复杂的交互场景

**缺点**:

1. **复杂度增加**:
   - 前端需要处理多种 Part 类型
   - 需要维护 Part 的状态
   - 需要处理流式更新

2. **存储开销**:
   - 存储大量的 Part 数据
   - 需要定期清理旧数据
   - 需要压缩机制

3. **格式转换开销**:
   - 需要将 Parts 转换为 AI 格式
   - 需要处理不同 AI 提供商的差异
   - 需要处理压缩和截断

**可能的设计问题**:

**问题 1: Part 类型过多,前端难以维护**

**解决方案**:
- 将 Part 分组(核心 Part vs 辅助 Part)
- 提供默认的渲染组件
- 支持自定义渲染器

**问题 2: 流式更新频率过高,性能问题**

**解决方案**:
- 节流(throttle)更新频率
- 批量更新多个 Part
- 使用虚拟滚动

**问题 3: 存储格式和 AI 格式不一致,维护困难**

**解决方案**:
- 明确定义转换规则
- 提供转换函数的单元测试
- 文档化转换逻辑

**问题 4: 某些 Part 既是输入又是输出,语义不清**

**解决方案**:
- 明确每种 Part 的输入/输出场景
- 提供类型定义和文档
- 在 API 文档中说明用法

**问题 5: snapshot 等字段对前端无用,浪费带宽**

**解决方案**:
- 提供精简的 API(只返回前端需要的字段)
- 支持字段过滤(如 `?fields=id,type,text`)
- 使用 GraphQL 让前端按需查询

**问题 6: 工具输出可能很大,影响性能**

**解决方案**:
- metadata 中截断输出(30KB)
- 完整输出按需加载(点击"查看完整输出")
- 支持分页加载大输出

### 8.7 Session 状态管理

**问题**: OpenCode 如何管理 Session 的状态?

**回答**:

**SessionStatus 模块**:
```typescript
// 文件: opencode/packages/opencode/src/session/status.ts:6-76
export namespace SessionStatus {
  export type Info = 
    | { type: "idle" }                    // 空闲
    | { type: "busy" }                    // 忙碌
    | { type: "retry"; attempt: number; message: string; next: number }  // 重试中
  
  // 获取状态
  export function get(sessionID: string): Info {
    return state()[sessionID] ?? { type: "idle" }
  }
  
  // 设置状态
  export function set(sessionID: string, status: Info) {
    // 1. 发布状态变更事件
    Bus.publish(Event.Status, { sessionID, status })
    
    // 2. 如果是 idle,清除状态
    if (status.type === "idle") {
      Bus.publish(Event.Idle, { sessionID })  // 向后兼容
      delete state()[sessionID]
      return
    }
    
    // 3. 更新状态
    state()[sessionID] = status
  }
}
```

**状态转换**:
```
idle → busy → idle
  ↓      ↓
  └─→ retry → busy → idle
```

**状态设置时机**:
```typescript
// 1. 开始处理消息
SessionStatus.set(sessionID, { type: "busy" })

// 2. LLM 调用失败,需要重试

  type: "retry",
  attempt: 1,
  message: "Rate limit exceeded",
  next: Date.now() + 5000,  // 5 秒后重试
})

// 3. 处理完成
SessionStatus.set(sessionID, { type: "idle" })
```

**客户端使用**:
```typescript
// 订阅状态变更
sdk.session.status().on("session.status", (evt) => {
  switch (evt.status.type) {
    case "idle":
      showInputBox()
      break
    case "busy":
      showSpinner()
      break
    case "retry":

})
```

### 8.10 如何实现 Session 的 Fork?

**问题**: Fork 的具体实现是什么?

**回答**:

**Fork 实现**:
```typescript
// 文件: opencode/packages/opencode/src/session/index.ts
export async function fork(input: {
  sessionID: string
  messageID?: string
}) {
  // 1. 获取父 Session
  const parent = await Session.get(input.sessionID)
  
  // 2. 创建子 Session
  const child = await Session.create({
    parentID: parent.id,
    title: `${parent.title} (fork)`,
    permission: parent.permission,  // 继承权限
  })
  
  // 3. 复制消息(到指定的 messageID)
  const messages = await Session.messages({ sessionID: parent.id })
  const targetIndex = input.messageID
    ? messages.findIndex(m => m.info.id === input.messageID)
    : messages.length - 1
  
  for (let i = 0; i <= targetIndex; i++) {
    const msg = messages[i]
    // 复制消息和 Parts
    await Session.updateMessage({
      ...msg.info,
      id: Identifier.create("message"),
      sessionID: child.id,
    })
    for (const part of msg.parts) {
      await Session.updatePart({
        ...part,
        id: Identifier.create("part"),
        sessionID: child.id,
        messageID: msg.info.id,
      })
    }
  }
  
  return child
}
```

**Fork 的用途**:

**1. 探索不同方案**:
```
原 Session:
├─ "实现用户认证"
├─ "使用 JWT"
└─ [实现中...]

Fork 1:
├─ "实现用户认证"  (复制)
└─ "使用 Session"   (新方向)

Fork 2:
├─ "实现用户认证"  (复制)
└─ "使用 OAuth"     (另一个方向)
```

**2. 回滚并重试**:
```
原 Session:
├─ "添加功能 A"
├─ "添加功能 B"
└─ "添加功能 C" (出错)

Fork from Message 2:
├─ "添加功能 A"  (复制)
├─ "添加功能 B"  (复制)
└─ "用不同方式添加功能 C"  (重试)
```

**3. 并行开发**:
```
主 Session:
└─ "重构认证系统"

Fork 1 (frontend):
└─ "更新前端认证逻辑"

Fork 2 (backend):
└─ "更新后端认证逻辑"

Fork 3 (tests):
└─ "添加认证测试"
```

export namespace MessageV2 {
  export function toModelMessage(messages: WithParts[]): ModelMessage[] {
    const result: ModelMessage[] = []
    
    for (const msg of messages) {
      const content = []
      
      for (const part of msg.parts) {
        if (part.type === "text") {
          content.push({
            type: "text",
            text: part.text,
            // 标记为可缓存(长文本)

      }
      
      result.push({ role: msg.info.role, content })
    }
    
    return result
  }
}

## 10. 总结

本文档深入分析了 OpenCode 和 KiloCode 的核心机制:

1. **上下文压缩**: KiloCode 采用混合触发(自动 + 手动),OpenCode 完全自动化
2. **权限管理**: KiloCode 缺乏细粒度权限,OpenCode 有完整的权限系统
3. **事件系统**: OpenCode 的 Bus 是神经中枢,实现模块解耦和实时通信
4. **快照回滚**: 基于 Git 的轻量级快照系统,支持非破坏性回滚
5. **Agent 系统**: 定义 AI 的行为模式、权限和工具集
6. **PTY vs TUI**: 两个不同层次的抽象,服务于不同用例
7. **Skill 系统**: 通过 Markdown 定义可复用的专业知识
8. **Parts 结构**: 细粒度的消息管理,支持流式更新和选择性压缩
9. **状态管理**: 通过 SessionStatus 管理 Session 的运行状态
10. **多模型支持**: 通过 Provider 抽象层支持多个 AI 提供商
11. **Session Fork**: 支持分支探索和并行开发

### 关键洞察

**架构哲学**:
- **KiloCode**: 简单、直观、面向任务
- **OpenCode**: 强大、灵活、面向对话

**技术选择**:
- **KiloCode**: 依赖 VSCode 生态,快速开发
- **OpenCode**: 自主实现,完全控制

**适用场景**:
- **KiloCode**: VSCode 用户,简单任务
- **OpenCode**: CLI 用户,复杂项目

**未来方向**:
- 两者可以互相借鉴
- 可以构建统一的抽象层
- 可以共享部分基础设施(MCP, Provider)

这些机制共同构成了现代 AI 编码助手的技术基础。
