# 0. 架构概览

## 系统定位

### 系统类型
OpenCode 是一个**多端 AI 编程助手平台**，包含：
- **CLI 工具**：核心命令行界面（主要交互方式）
- **桌面应用**：基于 Tauri 的跨平台桌面客户端
- **Web 控制台**：SaaS 管理平台（账户、计费、模型管理）
- **浏览器扩展**：VS Code 扩展支持

### 核心功能
一个开源的、提供商无关的 AI 编程代理，通过 TUI/GUI 与用户交互，支持多种 LLM 提供商，具备完整的工具调用能力（文件操作、代码搜索、LSP、终端执行等），并提供会话管理、权限控制和插件扩展机制。

### 主要用户场景
1. **代码开发与重构**：通过 `build` 代理执行文件编辑、代码生成、测试编写
2. **代码库探索与分析**：使用 `plan` 代理进行只读分析、架构规划
3. **复杂任务分解**：通过 `@general` 子代理并行执行多步骤任务
4. **企业级部署**：通过 Web 控制台管理团队、配额、自定义模型
5. **本地模型集成**：支持 Ollama、LM Studio 等本地 LLM 服务

## 技术栈

### 前端技术
- **框架**：SolidJS (响应式 UI)
- **桌面端**：Tauri 2.x (Rust + WebView)
- **Web 端**：SolidStart (SSR/SSG)
- **UI 库**：
  - `@kobalte/core` (无头组件)
  - `@opentui/solid` (TUI 组件)
  - `ghostty-web` (终端模拟器)
- **状态管理**：SolidJS 原生 Stores + Context
- **构建工具**：Vite 7.x + Bun

### 后端技术
- **运行时**：Bun (主要) + Node.js (兼容)
- **语言**：TypeScript (100%)
- **Web 框架**：Hono (轻量级 HTTP 路由)
- **数据库**：
  - PlanetScale (MySQL, 用于 Console)
  - 本地文件存储 (JSON, 用于 CLI/Desktop)
- **ORM**：Drizzle ORM
- **AI SDK**：Vercel AI SDK (`ai` package)
- **协议**：
  - MCP (Model Context Protocol) - 工具扩展
  - ACP (Agent Client Protocol) - 代理通信
  - LSP (Language Server Protocol) - 代码智能

### 基础设施
- **包管理**：Bun Workspaces (Monorepo)
- **构建系统**：
  - Turbo (并行构建)
  - Bun 原生构建
- **部署方式**：
  - CLI: npm/brew/scoop/nix 分发
  - Desktop: DMG/EXE/AppImage
  - Console: Cloudflare Workers (SST v3)
- **监控工具**：
  - Honeycomb (日志聚合)
  - OpenTelemetry (可选)
- **版本控制**：Git (项目通过 root commit hash 识别)

## 架构原则

### 1. 分层架构
项目遵循清晰的**三层架构**：

```
┌─────────────────────────────────────┐
│  Presentation Layer                 │  CLI/Desktop/Web
│  (packages/opencode, app, desktop)  │
├─────────────────────────────────────┤
│  Business Logic Layer               │  Agent/Session/Tool
│  (packages/opencode/src)            │  Registry
├─────────────────────────────────────┤
│  Data Layer                         │  Storage/Config/
│  (Storage, Config, Project)         │  Provider
└─────────────────────────────────────┘
```

**代码依据**：
- `packages/opencode/src/index.ts:1-160` - CLI 入口层
- `packages/opencode/src/agent/agent.ts:21-332` - 业务逻辑层
- `packages/opencode/src/storage/storage.ts:12-227` - 数据层

### 2. 模块边界
采用 **Namespace 模式** 组织代码，每个核心模块都是独立的命名空间：
- `Agent` - 代理管理
- `Session` - 会话生命周期
- `Tool` - 工具注册与执行
- `Provider` - LLM 提供商抽象
- `Storage` - 持久化层
- `Config` - 配置管理

**代码依据**：
- `packages/opencode/src/agent/agent.ts:21` - `export namespace Agent`
- `packages/opencode/src/session/index.ts:26` - `export namespace Session`
- `packages/opencode/src/tool/registry.ts:31` - `export namespace ToolRegistry`

### 3. 设计模式

#### 3.1 Plugin Architecture
通过 `ToolRegistry` 实现插件化工具系统：
- 内置工具（Bash, Read, Edit, Grep 等）
- 自定义工具（通过 `.opencode/tools/*.ts` 加载）
- MCP 工具（通过 Model Context Protocol 集成）

**代码依据**：`packages/opencode/src/tool/registry.ts:34-61`

#### 3.2 Provider Pattern
抽象 LLM 提供商接口，支持 20+ 提供商（Anthropic, OpenAI, Google, 本地模型等）

**代码依据**：`packages/opencode/src/provider/provider.ts`

#### 3.3 Event-Driven Architecture
使用 `Bus` 系统进行模块间通信：
- `Session.Event.Created`
- `MessageV2.Event.PartUpdated`
- `Project.Event.Updated`

**代码依据**：
- `packages/opencode/src/bus/bus-event.ts`
- `packages/opencode/src/session/index.ts:95-128`

### 4. 依赖注入/控制反转
使用 **Instance Context** 模式管理项目级状态：

```typescript
Instance.state(async () => {
  // 延迟初始化，自动清理
})
```

**代码依据**：
- `packages/opencode/src/project/instance.ts`
- `packages/opencode/src/agent/agent.ts:48-244` - Agent 状态管理

## 数据流概览

### 数据来源
1. **用户输入**：CLI/TUI 提示符、桌面应用输入框
2. **文件系统**：
   - 项目文件（通过 `Read`, `Glob`, `Grep` 工具）
   - 配置文件（`opencode.json`, `.opencode/` 目录）
3. **LLM API**：流式响应（通过 Vercel AI SDK）
4. **MCP 服务器**：外部工具调用结果
5. **本地存储**：
   - `~/.opencode/data/storage/` (会话、消息、项目元数据)
   - Git 仓库元数据（root commit hash 作为项目 ID）

### 数据流动方式
**单向数据流 + 事件驱动**：

```
User Input → Session → Agent → LLM Provider
                ↓
              Tools (Bash/Read/Edit/etc.)
                ↓
           File System / MCP
                ↓
          Storage (JSON)
                ↓
         Bus Events → UI Update
```

**关键流程**：
1. 用户消息 → `Session.create()` → `MessageV2.updateMessage()`
2. Agent 调用 LLM → 流式响应 → `updatePart()` → `Bus.publish()`
3. Tool 执行 → 权限检查 (`PermissionNext`) → 结果写入 Part
4. 会话状态 → `Storage.write()` → JSON 文件持久化

**代码依据**：
- `packages/opencode/src/session/index.ts:130-488`
- `packages/opencode/src/server/server.ts:62-520` - HTTP 路由层

### 数据最终去向
1. **UI 渲染**：通过 SSE (Server-Sent Events) 推送到前端
2. **持久化**：
   - 会话数据 → `~/.opencode/data/storage/session/{projectID}/{sessionID}.json`
   - 消息/Parts → 独立 JSON 文件（支持增量加载）
3. **外部 API**：
   - 分享功能 → S3 存储（通过 Console API）
   - 使用统计 → PlanetScale 数据库
4. **Git 仓库**：通过 `apply_patch` 工具直接修改文件

## 关键设计决策

### 决策 1：Bun 作为主要运行时

**决策内容**：
使用 Bun 替代 Node.js 作为 CLI 和构建工具的运行时。

**推断理由**：
- **性能优势**：Bun 的启动速度和执行效率显著优于 Node.js
- **内置工具链**：集成 bundler、test runner、package manager
- **TypeScript 原生支持**：无需额外编译步骤
- **兼容性**：保持 Node.js API 兼容，降低迁移成本

**替代方案**：
- Node.js + ts-node/tsx
- Deno (更激进的选择，但生态较小)

**代码依据**：
- `package.json:7` - `"packageManager": "bun@1.3.5"`
- `packages/opencode/package.json:12` - `"dev": "bun run --conditions=browser ./src/index.ts"`
- `packages/opencode/src/bun/index.ts` - Bun 专用工具封装

---

### 决策 2：JSON 文件存储 vs 数据库

**决策内容**：
CLI/Desktop 使用本地 JSON 文件存储会话数据，而非 SQLite 等嵌入式数据库。

**推断理由**：
- **简单性**：无需 schema 迁移，直接序列化 TypeScript 对象
- **可移植性**：用户可以直接查看/编辑会话文件
- **性能**：对于单用户场景，文件 I/O 足够快
- **增量加载**：消息和 Parts 分离存储，支持懒加载

**替代方案**：
- SQLite (更适合复杂查询)
- LevelDB/RocksDB (更高性能)

**代码依据**：
- `packages/opencode/src/storage/storage.ts:169-227` - 文件存储实现
- `packages/opencode/src/storage/storage.ts:24-142` - 数据迁移逻辑

---

### 决策 3：Client-Server 架构（本地 HTTP 服务）

**决策内容**：
CLI 和 Desktop 都运行本地 HTTP 服务器（默认端口 4096），前端通过 REST API + SSE 通信。

**推断理由**：
- **多客户端支持**：同一个后端可服务 TUI、Desktop、Web、移动端
- **热重载**：前端可独立开发，无需重启后端
- **远程访问**：支持通过 mDNS 在局域网内访问
- **协议标准化**：使用 OpenAPI 规范生成 SDK

**替代方案**：
- 单体应用（前后端耦合）
- IPC 通信（仅限本地）

**代码依据**：
- `packages/opencode/src/server/server.ts:537-577` - 服务器启动逻辑
- `packages/opencode/src/server/server.ts:62-520` - Hono 路由定义
- `README.md:111` - "A client/server architecture"

---

### 决策 4：权限系统设计

**决策内容**：
实现细粒度的权限控制系统 (`PermissionNext`)，支持工具级、文件级、目录级权限配置。

**推断理由**：
- **安全性**：防止 AI 意外修改关键文件（如 `.env`）
- **灵活性**：不同 Agent 可配置不同权限（如 `plan` 模式禁止编辑）
- **用户控制**：支持 `ask`/`allow`/`deny` 三种策略
- **模式匹配**：支持 glob 模式和正则表达式

**替代方案**：
- 全局开关（过于粗糙）
- 沙箱环境（性能开销大）

**代码依据**：
- `packages/opencode/src/permission/next.ts` - 权限系统实现
- `packages/opencode/src/agent/agent.ts:51-69` - 默认权限配置
- `packages/opencode/src/config/config.ts:472-537` - 权限配置 Schema

---

### 决策 5：Monorepo 结构

**决策内容**：
使用 Bun Workspaces 管理多个包（`opencode`, `app`, `desktop`, `console`, `sdk`, `ui` 等）。

**推断理由**：
- **代码共享**：UI 组件、工具函数在多个客户端间复用
- **类型安全**：跨包引用保持类型检查
- **统一构建**：Turbo 并行构建所有包
- **版本同步**：所有包使用相同版本号（`1.1.26`）

**替代方案**：
- 多仓库（增加维护成本）
- 单包（代码耦合度高）

**代码依据**：
- `package.json:16-22` - Workspaces 配置
- `turbo.json` - Turbo 构建配置
- `packages/` - 17 个子包
